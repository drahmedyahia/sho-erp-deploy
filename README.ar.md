# حزمة نشر Sho-ERP

**العربية** · [English](README.md)

مجلد واحد يشغّل Sho-ERP مع خدمات Supabase التي يحتاجها: التطبيق وستّ حاويات Supabase
(`db` و`auth` و`rest` و`realtime` و`storage` و`api-gw`). Studio و`meta` (واجهة إدارة القاعدة) اختياريان.
غير مضمَّن لأن التطبيق لا يستعمله: edge functions وimage proxy وconnection pooler وanalytics وشحن السجلات.

## البداية السريعة

كل طرق التثبيت في المولّد: <https://shoerp.sho-labs.com> (أو `generator.html` في هذا المجلد، ولا يحتاج إنترنت). تختار
**كامل** أو **منفصل**، ثم **سكربت** أو **compose**، فيعطيك ما تحتاجه تلك الطريقة بالضبط: أمر SSH مع متطلباته، أو ملف
compose و`.env` مع بيانات الاتصال. وهذه الأوامر نفسها للمرجع:

|                                           | **بسكربت** (SSH، داخل مجلد `deploy/`)                                | **بملف compose** (Dockge وPortainer وواجهة رسومية)               |
| ----------------------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------- |
| **أ. كل شيء** (التطبيق + Supabase)        | `sudo sh install.sh https://api.example.com https://erp.example.com` | المولّد، **كل شيء**: `compose.yaml` + `.env`                     |
| **ب. Supabase وحده** (تربط التطبيق بنفسك) | `sudo sh install.sh --supabase-only https://api.example.com`         | المولّد، **Supabase فقط**: `supabase-only.compose.yaml` + `.env` |

خيارات **ب** (يختارها المولّد عنك بحسب المكان الذي يعمل فيه تطبيقك؛ التفصيل في _طريقتان للنشر_):

```sh
sudo sh install.sh --supabase-only --db-bind 172.17.0.1 https://api.example.com   # انشر منفذ القاعدة على هذا العنوان أيضًا
sudo sh install.sh --supabase-only --network second https://api.example.com        # مشروع Supabase ثانٍ على الخادم نفسه
```

قبل السكربت: Docker مع Compose v2 على الخادم، ونسخ مجلد `deploy/` هذا إليه (الخطوات 1 إلى 3 أدناه). يولّد السكربت وملفات
compose أسرارًا مختلفة كلٌّ بنفسه: اختر طريقة واحدة لكل تثبيت ولا تخلط بينهما.

## المتطلبات

- Docker مع Compose v2 (Container Manager على Synology DSM)، معمارية x86_64.
- نحو 2 جيجا ذاكرة و5 جيجا قرص لتثبيت صغير.
- اتصال خارجي بالإنترنت من الخادم: لسحب الصور ولتفعيل كود الترخيص.

## خطوة بخطوة على أي خادم

الخطوات واحدة على أي خادم Linux (VPS أو جهاز سحابي أو جهاز في مكتبك أو NAS يشغّل Docker). المختلف فقط
طريقة الوصول إلى الجهاز والوكيل العكسي.

1. **اتصل عبر SSH** من حاسوبك (على ويندوز استعمل PuTTY أو Windows Terminal):

   ```sh
   ssh <المستخدم>@<عنوان الخادم>          # أضف -p <المنفذ> إن لم يكن SSH على 22
   ```

   أوامر Docker تحتاج صلاحية مدير: ابدأها بـ `sudo`، أو افتح صدفة root مرة واحدة بـ `sudo -i`. في بعض أجهزة
   NAS يكون SSH مغلقًا افتراضيًا؛ فعّله من إعدادات النظام.

2. **ثبّت Docker** مع Compose v2 إن لم يكن موجودًا. تحقق بـ `docker --version` و`docker compose version`.
   التعليمات الرسمية: <https://docs.docker.com/engine/install/>.

3. **انسخ مجلد `deploy/` إلى الخادم** في مكان ثابت (البيانات تُحفظ داخله):

   ```sh
   scp -r deploy <المستخدم>@<عنوان الخادم>:/opt/sho-erp          # من حاسوبك
   # أو على الخادم (مستودع النشر العام فيه هذا المجلد فقط):
   git clone --depth 1 https://github.com/drahmedyahia/sho-erp-deploy.git /opt/sho-erp/deploy
   ```

4. **سجّل الدخول إلى سجل الصور**، فقط إن كنت تستعمل صورة خاصة (الصورة الرسمية عامة ولا تحتاج تسجيل دخول). عندها تُعطى اسم مستخدم ورمز وصول (صلاحية
   `read:packages`) مع الترخيص. اكتب الرمز عند الطلب، لا في سطر الأمر:

   ```sh
   sudo docker login ghcr.io -u <اسم المستخدم>
   ```

   سجّل الدخول بالمستخدم نفسه الذي يشغّل المثبّت (`sudo` هنا يطابق `sudo sh install.sh`). ظهور الخطأ
   `unauthorized` أثناء السحب يعني أن هذه الخطوة ناقصة أو نُفّذت بمستخدم آخر.

5. **تأكد أن المنفذين فارغان** (3000 للتطبيق و8000 للبوابة). إن كان برنامج آخر يستعملهما فاضبط `APP_PORT`
   و`API_GW_HTTP_PORT` في `.env` أولًا (انسخ `.env.example` إلى `.env`):

   ```sh
   docker ps --format '{{.Names}}\t{{.Ports}}' | grep -E ':3000->|:8000->'
   netstat -ltn | grep -E ':3000 |:8000 '      # أو: ss -ltn (غير مثبّت في كل نظام)
   ```

6. **ثبّت**، بالاسمين العامين اللذين ستعطيهما للمستخدمين (انظر _العناوين والوكيل العكسي_):

   ```sh
   cd /opt/sho-erp
   sudo sh install.sh https://api.example.com https://erp.example.com
   ```

7. **أنشئ الوكيل العكسي** للاسمين (أي وكيل؛ `Caddyfile.example` جاهز) وافتح الجدار الناري للمنفذين 80 و443
   فقط. لا تنشر المنافذ 3000 و8000 ولا منفذ قاعدة البيانات على الإنترنت.

8. **تحقق**: يجب أن ينتهي `sudo sh doctor.sh` بلا `[FAIL]`. ثم افتح عنوان التطبيق **في متصفح** (هذا ما يبدأ تثبيت قاعدة البيانات).

كل تركيب مستقل: مجلده و`.env` وقاعدته. يمكن لعدة تراكيب أن تتشارك خادمًا واحدًا إن كان لكل منها مجلد ومنافذ خاصة.

## التثبيت

1. انسخ مجلد `deploy/` إلى الخادم.
2. شغّل المثبّت بعنوان بوابة API العام ثم عنوان التطبيق:

   ```sh
   sh install.sh https://api.example.com https://erp.example.com
   ```

   لتجربة سريعة داخل الشبكة يمكنك استعمال عناوين عادية: `sh install.sh http://192.168.1.10:8000 http://192.168.1.10:3000`

يولّد المثبّت كل الأسرار في `.env` (دون أن يستبدل الموجود)، ويغلق التسجيل العام، ويسحب الصور، ويشغّل كل
شيء، ثم يجري فحصًا ذاتيًا نهائيًا. **قد يستغرق أول تشغيل عدة دقائق على قرص بطيء** (كل خدمة تنفّذ هجراتها
الأولى)، والمثبّت ينتظر ذلك.

عند الانتهاء افتح عنوان التطبيق **في متصفح**: هذا ما يبدأ تثبيت مخطط قاعدة البيانات (دقائق قليلة؛ الطلب المجرد مثل `curl` لا
يبدؤه). أول مدير هو `admin@local.com` بكلمة السر المؤقتة `admin1234`، وتُجبَر على
اختيار كلمة سر جديدة عند أول دخول. ثم أدخل كود الترخيص الذي أُعطيتَه.

## التثبيت بلا SSH (Dockge وPortainer وأي واجهة رسومية)

إن كنت تدير Docker من واجهة ويب فلا تحتاج طرفية إطلاقًا. يكفي ملفان:

1. افتح **`generator.html`** (نزّله من هذا المجلد وافتحه بنقرتين، أو استعمل النسخة المستضافة من الصفحة نفسها:
   <https://shoerp.sho-labs.com>). تعمل داخل متصفحك فقط: الأسرار تُولَّد هناك ولا تُرسَل إلى أي مكان. اكتب عنوانيك العامين واضغط **ولّد**.
2. في واجهتك أنشئ مشروعًا/Stack جديدًا والصق الملفين اللذين تعرضهما الصفحة: **`compose.yaml`** (هو نفسه
   `standalone/compose.yaml` في هذا المجلد) و**`.env`**، ثم انشر. الصفحة تسرد النقرات بدقة لـ Dockge وPortainer
   وSynology Container Manager.

الفروق عن التثبيت بالطرفية أعلاه:

- يلزم **Docker Compose v2** (`docker compose version`)؛ ملفات الإعداد مضمَّنة داخل `compose.yaml` (تكتبها حاويتا القاعدة
  والبوابة عند بدئهما) فلا يُرفع شيء آخر.
- البيانات في **مجلدات مسمّاة** (`db-data` و`storage-data` و`app-data`) يديرها Docker (على Synology تحت
  `/volume1/@docker/volumes/<المشروع>_<الاسم>/_data`؛ الأمر `docker volume inspect <الاسم>` يعرض المسار) بدل `./volumes`،
  فلا تنطبق `backup.sh` و`restore.sh` و`upgrade.sh`. استعمل شاشة النسخ الاحتياطي داخل التطبيق، أو انسخ المجلدات المسمّاة بـ Docker.
- تفضّل أن ترى بياناتك؟ في **خيارات متقدمة** في الصفحة اكتب **مجلد البيانات** (مسار مطلق مثل
  `/volume1/docker/sho-erp/data`). فتُحفَظ القاعدة في `db/` والملفات في `storage/` داخله. أنشئ المجلدين **أولًا** (`sudo mkdir -p <المجلد>/db <المجلد>/storage`؛ والصفحة تعرض الأمر بدقة): Docker لا ينشئهما
  ويفشل النشر بخطأ _Bind mount failed ... does not exist_. ويجب أن يكونا على الجهاز الذي يشغّل Docker. تُكتَب `DB_DATA` و`STORAGE_DATA` في `.env`؛ احذف هذين السطرين
  للعودة إلى المجلدات المسمّاة (لا ينقل ذلك بيانات مخزَّنة بالفعل). مجلد إعدادات التطبيق الصغير (`app-data`) يبقى مسمّى دائمًا.
- **خذ الملفين وبيانات الاتصال من ضغطة واحدة على «ولّد».** كل ضغطة تصنع أسرارًا جديدة كليًا، والقاعدة تحتفظ بالأسرار
  التي بدأت بها أول مرة، فلا يصح `.env` من ضغطة مع بطاقة من أخرى. تعرض الصفحة **بصمة** من ست خانات لهذا التوليد، ويحملها
  أول سطر في `.env`: على الخادم يجب أن يُظهر `head -n 1 .env` الرمز نفسه. وإن اختلف فابدأ من توليد واحد (وأفرغ مجلد بيانات
  القاعدة أولًا إن كانت قد بدأت).
- **احفظ ملف `.env`** الذي تعرضه الصفحة مرة واحدة: لا يُخزَّن في أي مكان آخر، وضياعه يعني ضياع القدرة على فك تشفير
  البيانات المخزنة.
- فقط إن كنت تستعمل صورة خاصة (الرسمية عامة) فسجّل الدخول إلى السجل مرة واحدة على الخادم (`docker login ghcr.io`).

`generator.html` والملفان في `standalone/` يُولَّدان من `docker-compose.yml` و`volumes/` بالأمر
`node utils/build-standalone.mjs` (يفشل اختبار إن كانا غير محدّثين)، فالطريقتان تركّبان النظام نفسه.

## طريقتان للنشر، وكل منهما بسكربت أو بملف compose

|                                             | **أ. كل شيء (التطبيق + Supabase)**         | **ب. Supabase وحده، ويُربط التطبيق به على حدة**                           |
| ------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------- |
| **بسكربت** (طرفية على الخادم)               | `sh install.sh`                            | `sh install.sh --supabase-only`                                           |
| **بملف compose** (Dockge وPortainer وواجهة) | `standalone/compose.yaml` (يولّده المولّد) | `standalone/supabase-only.compose.yaml` (يولّده المولّد)                  |
| ما يعمل                                     | التطبيق وحاويات Supabase الست              | حاويات Supabase فقط (القاعدة والدخول وrest وrealtime والملفات والبوابة)   |
| بيانات الاتصال                              | تُولَّد في `.env`، لا تكتب شيئًا           | تُطبع (السكربت) أو تظهر في بطاقة (المولّد)، وتُدخلها مرة في شاشة `/setup` |
| الأنسب لـ                                   | عميل أو خادم واحد؛ الأبسط                  | Supabase تريده مستقلًا عن التطبيق، أو تطبيق مثبّت أصلًا                   |

**أ** هي ما تشرحه الأقسام أعلاه (السكربت: التثبيت؛ compose: التثبيت بلا SSH).

**ب** خطوتان: أنشئ Supabase (أدناه)، ثم اربط التطبيق به في شاشة `/setup`.

**ب هي الطريقة الموصى بها حين يُحدَّث التطبيق كثيرًا**، لأن قاعدة البيانات تعيش في مشروعها الخاص:

- تحديث التطبيق يعني «اسحب الصورة الجديدة وأعد نشر مشروع التطبيق». لا يُوقَف Supabase ولا يُعاد تشغيله ولا يُمَسّ
  أصلًا، فلا توجد لحظة في التحديث تتعرض فيها البيانات للخطر، ولا انتظار لإقلاع القاعدة من جديد (على قرص بطيء
  يأخذ الانتظار دقائق).
- يمكن إيقاف مشروع التطبيق أو إعادة نشره أو الرجوع إلى صورة أقدم أو حذفه (حتى بالخطأ: `docker compose down` في
  المكان الخطأ، أو مجلد خاطئ، أو مشروع حُذف من الواجهة) دون أن تتأثر القاعدة أو أقراصها.
- يتغير Supabase حين تقرر أنت تحديثه فقط، كخطوة مقصودة مستقلة ولها نسخها الاحتياطي (`backup.sh`). أما في أ فمشروع
  واحد يضم الاثنين، فقد يعيد تحديث الحزمة إنشاء حاويات القاعدة في التشغيل نفسه.
- يمكن نقل كل جزء أو نسخه احتياطيًا أو استرجاعه على حدة.

تبقى أ الأبسط لخادم واحد نادر التغيير؛ اختر ب حين تصير البيانات أهم من الراحة.

### ب، الخطوة 1: أنشئ Supabase وحده

في الطريقتين السؤال الأول هو **أين يعمل تطبيقك؟**، فهو يحدد كيف يصل التطبيق إلى القاعدة:

| أين يعمل التطبيق                                    | كيف يصل إلى القاعدة                                                                             | منفذ القاعدة                              |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------- |
| **في حاوية Docker على هذا الخادم** (موصى به)        | ينضم التطبيق إلى شبكة Docker الخاصة بالمشروع ويتصل بـ `<الشبكة>-db:5432`                        | **لا يُنشر أي منفذ**، فلا تعارض ولا تعريض |
| في حاوية على هذا الخادم دون تعديل compose الخاص بها | منفذ منشور على عنوان بوابة شبكة Docker التي يعمل عليها التطبيق (`172.17.0.1` للشبكة الافتراضية) | منشور هناك فقط                            |
| على هذا الخادم خارج Docker، أو عبر نفق SSH          | `127.0.0.1`                                                                                     | منشور على `127.0.0.1` فقط                 |
| على جهاز آخر                                        | عنوان الخادم نفسه                                                                               | منشور على كل العناوين: لشبكة موثوقة فقط   |

**بملف compose**: افتح `generator.html` (أو <https://shoerp.sho-labs.com>) واختر **Supabase فقط (بدون التطبيق)**،
وأجب عن السؤال، وأنشئ المشروع من الملفين اللذين تعرضهما الصفحة. تعرض الصفحة أيضًا **بطاقة بيانات الاتصال**
(رابط القاعدة وفيه العنوان الصحيح جاهزًا، وعنوان المشروع، والمفتاح العام، ومفتاح الخدمة)، وفي الخيار الأول
**المقطع الذي يُضاف إلى compose تطبيقك** ليدخل الشبكة. الملفان: `standalone/supabase-only.compose.yaml`
(بلا منفذ للقاعدة) و`standalone/supabase-only-db-port.compose.yaml` (ينشر المنفذ أيضًا).

**بسكربت**:

```sh
sh install.sh --supabase-only https://api.example.com                      # ينضم التطبيق إلى الشبكة
sh install.sh --supabase-only --db-bind 172.17.0.1 https://api.example.com # نشر المنفذ على هذا العنوان
```

الخيارات: `--project NAME` (مشروع Compose أي اسم الـ stack: بادئة أسماء الحاويات والأقراص، والافتراضي `sho-erp`؛ ويصلح للطريقة أ أيضًا)، و`--network NAME` (شبكة Docker، والافتراضي `sho-supabase`؛ استعمل اسمًا آخر لمشروع ثانٍ على الخادم نفسه)،
و`--db-bind ADDRESS`، و`--db-port PORT` (الافتراضي `55432`؛ وإن كان مشغولًا يستعمل السكربت أول منفذ حر ويخبرك)،
و`--db-host ADDRESS` (العنوان في رابط القاعدة حين يكون `--db-bind` هو `0.0.0.0`). يطبع السكربت بيانات الاتصال،
وحين ينضم التطبيق إلى الشبكة يطبع المقطع الذي يُضاف إلى compose التطبيق. ويعمل `doctor.sh` و`backup.sh` و`upgrade.sh`
كالمعتاد (يكتب السكربت `COMPOSE_FILE` في `.env`، فتستعمل أوامر `docker compose ...` العادية الملفات نفسها).

ملاحظات:

- **اسم الـ stack.** يستعمل Dockge وPortainer الاسم الذي تعطيه للـ stack هناك. وفي الطرفية هو اسم المجلد ما لم تحدد غيره:
  خانة **اسم المشروع (stack)** في المولّد تكتب `COMPOSE_PROJECT_NAME` في `.env`، ويقبل السكربت `--project NAME`. اختره قبل
  أول تشغيل: تغييره لاحقًا ينشئ مشروعًا جديدًا (حاويات وأقراصًا جديدة؛ والبيانات في مجلد اخترته تبقى فيه).
- اسم الشبكة يحدد أيضًا اسم القاعدة عليها (`<الاسم>-db`)، فمشروعا Supabase على خادم واحد يحتاجان اسمين مختلفين.
- منفذ القاعدة المنشور لا تحميه إلا كلمة سره، والاتصال به غير مشفّر: أبقه على `127.0.0.1` أو على عنوان بوابة Docker،
  ولا تفتحه للإنترنت أبدًا. وإن فشل النشر بخطأ _address already in use_ فالمنفذ مستعمل: غيّر `DB_PORT` في `.env`
  (وفي رابط القاعدة) وانشر من جديد.
- `SUPABASE_INTERNAL_URL: http://api-gw:8000` في متغيرات التطبيق اختياري ومنصوح به (يتضمنه مقطع المولّد ومخرجات السكربت):
  فتبقى نداءات خادم التطبيق إلى Supabase داخل الشبكة. بدونه تستعمل العنوان العام، ويجب أن يصل إليه من حاوية التطبيق (مثل
  DNS داخلي يوجّهه إلى وكيلك العكسي)؛ وفي خادم لا يستطيع راوتره الرجوع إلى عنوانه العام تفشل (`fetch failed` في سجل
  التطبيق، ولا يُنشأ حساب المدير الأول). والإصدارات الحديثة من التطبيق تكتشف ذلك بنفسها عند الإقلاع وعند حفظ `/setup` للاتصال، وأيضًا
  إن توقف العنوان العام عن الرد أثناء عملها: إن تعذر الوصول إليه وردّت `api-gw` على الشبكة المشتركة استعملتها حتى إعادة التشغيل
  التالية (ويعطّل ذلك `SUPABASE_INTERNAL_URL_AUTO=off`). وأبقِ
  التطبيق على شبكته الحالية إضافة إلى هذه.
- القاعدة فارغة (بلا جداول) حتى يتصل بها التطبيق: يثبّت التطبيق جداوله عند أول اتصال.
- أعطِ المشروع شبكة Docker خاصة به: لا تصل حاوياته بشبكة مشتركة مع مشاريع أخرى (انظر التحذير في التثبيت بلا SSH).

### ب، الخطوة 2: اربط التطبيق (شاشة `/setup`)

في المولّد، يبني خيار **Supabase فقط** مع أدوات compose أيضًا **ملف compose لتطبيقك** (الاسم والمنفذ ومجلد البيانات وشبكة
وكيلك العكسي وهل ينضم إلى شبكة Supabase، ورمز `SETUP_TOKEN` مولَّد)، مكتوبًا من `docker-compose.yml` في المستودع؛ استعمله
كمشروع مستقل، أو ادمج المقطع الذي يعرضه في الملف الذي عندك.

شغّل صورة التطبيق وحدها بملف `docker-compose.yml` الموجود في جذر المستودع، واضبط `SETUP_TOKEN` بقيمة
عشوائية طويلة (مثل `openssl rand -hex 24`). بدون توكن تكون الشاشة معطّلة. افتح `https://<تطبيقك>/setup`
وأدخل التوكن ثم:

| الحقل                | من أين تحصل عليه                                                                                                                                                                                                          |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| رابط قاعدة البيانات  | `postgresql://postgres:<كلمة السر>@<عنوان القاعدة>:5432/postgres`. الاتصال **المباشر** لا الـpooler. من الخطوة 1: البطاقة أو مخرجات السكربت. في Supabase Cloud: Project Settings > Database > Connection string (direct). |
| عنوان الـAPI         | العنوان العام لواجهة Supabase (الخطوة 1: العنوان الذي كتبته؛ Cloud: Project Settings > API).                                                                                                                              |
| المفتاح العام (anon) | `ANON_KEY` (الخطوة 1) أو مفتاح `anon` / publishable (Cloud).                                                                                                                                                              |
| مفتاح الخدمة         | `SERVICE_ROLE_KEY` (الخطوة 1) أو مفتاح `service_role` / secret (Cloud).                                                                                                                                                   |
| معرّف المشروع        | أي اسم تختاره (Cloud: مرجع المشروع).                                                                                                                                                                                      |

الشاشة نفسها تربط تطبيقًا بمشروع Supabase Cloud، فلا تلزم تلك الحالةَ الخطوةُ 1.

ملاحظات:

- كل تطبيق يحتاج **قاعدة بيانات خاصة به**؛ لا يجوز أن يتشارك تطبيقان قاعدة واحدة.
- القيم تُحفظ في `/app/data/connection.json` داخل قرص بيانات التطبيق و**تتقدم على متغيرات البيئة**، فاحتفظ بذلك
  القرص وانسخه احتياطيًا. ولاحقًا يستطيع المدير تعديلها من `/setup?edit=1` دون التوكن.
- أفرغ `SETUP_TOKEN` بعد انتهاء الإعداد.

## العناوين والوكيل العكسي

لا حاجة لإظهار عناوين IP للمستخدمين. ضع وكيلًا عكسيًا بشهادة HTTPS (Nginx Proxy Manager أو Nginx أو
Caddy أو Traefik) واستعمل اسمين:

| الاسم             | يوجَّه إلى (http) | ملاحظات                                       |
| ----------------- | ----------------- | --------------------------------------------- |
| `erp.example.com` | `<الخادم>:3000`   | HTTPS                                         |
| `api.example.com` | `<الخادم>:8000`   | HTTPS مع تفعيل **WebSocket** (التحديث اللحظي) |

قواعد مهمة:

- نوع الوجهة **http**: الحاويات لا تنهي اتصال TLS بنفسها.
- الاسمان يجب أن يكونا **https** كلاهما. الصفحة على https لا تستطيع الاتصال ببوابة http (يحجبها المتصفح
  كمحتوى مختلط ويعرض درعًا أحمر).
- إن كان الوكيل على الجهاز نفسه فاضبط في `.env`: `APP_BIND=127.0.0.1` و`API_GW_BIND=127.0.0.1`.
- الوكيل الموجود على عنوان شبكة macvlan لا يستطيع الوصول إلى عنوان الجهاز نفسه. وجّه إلى بوابة شبكة
  Docker المشتركة مع الجهاز (مثل `172.17.0.1`) والمنفذ المنشور. ولا تحلّ ذلك بوصل المشروع بشبكة الوكيل
  (انظر التحذير أدناه).
- ملفات النسخ الكبيرة لا تحتاج أي إعداد في البروكسي: شاشة الاسترجاع ترفعها على أجزاء حجم كل منها 4 ميجابايت،
  فلا يوجد طلب كبير. لا تضف تعليمات Nginx مخصصة للمضيف إلا للضرورة: تعليمة خاطئة أو مكرّرة تجعل
  Nginx Proxy Manager يُسقط المضيف كله بصمت (يبقى يظهر "Online" لكن اتصال TLS يفشل بخطأ
  _unrecognized name_).
- **لا تصل حاويات المشروع بشبكة Docker مشتركة** (مثل شبكة الوكيل العكسي) لتصل إليها بالاسم. في كل مشروع Supabase
  خدمات اسمها `rest` و`auth` و`db` و`storage` و`realtime`؛ والبوابة تجد خدماتها بهذه الأسماء، فعلى شبكة مشتركة قد
  تتصل بحاوية من **مشروع آخر** وتقرأ أو تكتب في قاعدته. أبقِ كل مشروع على شبكته الخاصة التي ينشئها Compose، ووجّه
  الوكيل إلى المنافذ المنشورة (`<عنوان الجهاز>:<المنفذ>`).
- خادم التطبيق يتصل بالبوابة مباشرة داخل شبكة Docker (`SUPABASE_INTERNAL_URL`)، فالوكيل للمتصفحات فقط.

لتغيير العناوين لاحقًا عدّل `SUPABASE_PUBLIC_URL` و`API_EXTERNAL_URL` (يجب أن ينتهي بـ`/auth/v1`) و`SITE_URL`
في `.env` ثم نفّذ `docker compose up -d auth app`.

## الأوامر اليومية

```sh
docker compose ps                       # حالة كل حاوية
docker compose logs -f app              # متابعة سجل التطبيق
sh doctor.sh                            # فحص ذاتي: ما المشكلة وكيف تُحل
sh backup.sh                            # قاعدة + تخزين + .env في backups/<التاريخ>/
sh restore.sh backups/<المجلد>          # استرجاع نسخة (يطلب تأكيدًا)
sh upgrade.sh                           # نسخة احتياطية ثم سحب الصور الجديدة ثم إعادة تشغيل
docker compose --profile admin up -d    # تشغيل Studio (للمسؤولين فقط)
```

**جرّب `restore.sh` على نسخة تجريبية قبل أن تعتمد على النسخ الاحتياطية.**

## إعدادات لا بد من إكمالها

- **البريد**: من داخل التطبيق، الإعدادات ← البريد الإلكتروني. اضبط SMTP وفعّله. التطبيق يرسل رسائل
  استرداد كلمة السر بنفسه؛ متغيرات `SMTP_*` في `.env` غير مستعملة. بدون البريد يبقى الاسترداد برمز
  الاسترداد فقط.
- **الترخيص**: يطلب التطبيق كود التفعيل بعد أول دخول ويتحقق منه لدى سيرفر الترخيص، فيجب أن يصل الخادم
  إليه عبر الإنترنت.
- **Studio** (اختيارية) تمنح تحكمًا كاملًا بالقاعدة خلف `DASHBOARD_USERNAME` و`DASHBOARD_PASSWORD` في
  `.env`. أبقِها متوقفة إلا عند الحاجة.

## حل المشاكل

شغّل `sh doctor.sh` أولًا؛ يطبع ما المشكلة وماذا تفعل. حالات شائعة:

| العَرَض                                       | السبب المرجّح والحل                                                                       |
| --------------------------------------------- | ----------------------------------------------------------------------------------------- |
| حاويات `unhealthy` بعد أول تشغيل مباشرة       | ما زالت تهيّئ نفسها على قرص بطيء. انتظر 2-3 دقائق ثم `docker compose up -d --wait`.       |
| كل الطلبات ترد 503 خلال أجزاء من الثانية      | البوابة لا تجد auth/rest. نفّذ `docker compose restart api-gw`.                           |
| الدخول يقول "بيانات خاطئة" بعد التثبيت مباشرة | يُنشأ أول مدير الآن؛ يعرض التطبيق شاشة "جارٍ الإعداد" حتى نحو 90 ثانية.                   |
| درع أحمر / محتوى مختلط في المتصفح             | الموقع https لكن `SUPABASE_PUBLIC_URL` على http. اجعلهما https ثم `docker compose up -d`. |
| "Could not reach the license server"          | لا إنترنت خارجي للحاوية أو جدار ناري يمنعها. `sh doctor.sh` يعرض الخطأ بالتحديد.          |
| خطأ TLS ‏_unrecognized name_ على اسم الـAPI   | مضيف الوكيل بلا إعداد صالح (غالبًا تعليمة Nginx مخصصة خاطئة). احذفها واحفظ.               |

## ملاحظات أمنية

- `.env` يحوي كل الأسرار. احتفظ بنسخة في مكان آمن ولا ترفعه إلى git. فقدانه يعني فقدان القدرة على فك
  تشفير البيانات المخزنة.
- التسجيل العام مغلق (`DISABLE_SIGNUP=true`)؛ المستخدمون يُنشَأون من داخل التطبيق.
- لا تنشر منفذ القاعدة. إن احتجت أداة SQL خارجية فاربطه بـ`127.0.0.1` فقط (كتلة `ports` المعلّقة تحت
  `db`) واتصل عبر نفق. ولأوامر SQL السريعة استعمل:
  `docker compose exec db psql -U postgres -d postgres`.

## الملفات

- `docker-compose.yml`: مقتطف من ملف Supabase الرسمي (self-hosted v0.8.0) مضافًا إليه التطبيق.
- `install.sh` و`doctor.sh` و`backup.sh` و`restore.sh` و`upgrade.sh`: العمليات.
- `.env.example`: قالب الإعداد (الأسرار تُولَّد ولا تُكتب يدويًا).
- `volumes/`: إعدادات البوابة وSQL تهيئة القاعدة المأخوذة من Supabase؛ انظر `NOTICE` (تعديل واحد مقصود:
  البحث بـIPv4 فقط في `volumes/api/envoy/cds.yaml`).
- `Caddyfile.example`: وكيل عكسي بسيط بشهادة HTTPS تلقائية.
- `generator.html` و`standalone/*.yaml`: التثبيت بلا SSH وحزم Supabase وحده (يولّدها `utils/build-standalone.mjs`).
- `docker-compose.supabase-only.yml` و`docker-compose.supabase-db-port.yml`: ما يضيفه `sh install.sh --supabase-only` إلى `docker-compose.yml`.
- `LICENSE-supabase` و`NOTICE`: إسناد Apache-2.0 للملفات المشتقة من Supabase.
